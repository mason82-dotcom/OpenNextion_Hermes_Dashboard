# Hermes Touch v0.8 – Diagnose der ESP32-Speicherreserven (Entwicklungsstand)

**Status: im GitHub-Quellcode implementiert, noch NICHT auf dem Pi kompiliert oder am ONX3248G035 getestet.** Die auf dem Gerät installierte, bewährte Firmware bleibt zunächst v0.7. v0.7.1 bezeichnet die bereits geprüften Änderungen an der Pi-Bridge und den Build-Skripten.

## Neuer Umfang

Die SYSTEM-Seite enthält sechs statt vier Zeilen im vorhandenen 320×480-Layout:

1. `Heap: N KB | Min: M KB` – aktuell freier und seit Boot kleinster freier Heap-Wert, aus `ESP.getFreeHeap()` / `ESP.getMinFreeHeap()`.
2. `Groesster Block: N KB` – größter zusammenhängender freier interner 8-Bit-Heapblock aus `heap_caps_get_largest_free_block(MALLOC_CAP_INTERNAL | MALLOC_CAP_8BIT)`. Dieser Wert hilft, Fragmentierung zu erkennen.
3. `PSRAM: N / M KB frei` – freier und gesamter PSRAM, unverändert.
4. `TLS-Stack min. frei: N B` – die kleinste bisher vom dedizierten HTTPS-FreeRTOS-Task beobachtete **verbleibende Stackreserve in Bytes**. Gemessen im Task **nach** dem HTTPS-Poll; die Anzeige erhält ausschließlich den Mutex-geschützten Telemetrie-Snapshot. Das ESP-IDF-FreeRTOS-API liefert High-Water-Mark in Bytes. Im Offline-Modus erscheint `TLS-Task: OFFLINE`.
5. `Laufzeit: N Minuten` – lokale ESP32-Laufzeit.
6. `Touch-Aktionen: N` – lokaler Bedienungszähler.

Die Hardware-Informationskarte wurde kompakter; die neue Diagnostikkarte endet vor der unteren Tab-Navigation. Die übrigen Reiter **STATUS**, **GRAPH**, **CHAT** bleiben unverändert. Insbesondere gibt es keine neuen Netzwerk-Endpunkte, Geräte-/Hermes-Schreibbefehle oder Geheimnisse im Repository.

**Interpretation:** Ein sinkendes momentanes Heap-/Blockniveau oder eine schrumpfende Stackreserve ist nicht automatisch ein Leak. Der Mindest-Heap und die Task-High-Water-Mark sind bewusst seit Boot monotone Tiefstwerte. Für einen Speicherverlust muss zusätzlich ein über Zeit anhaltender Trend unter vergleichbaren Bedingungen nachgewiesen werden.

## Zuerst auf dem Pi prüfen – ohne Flashen

```bash
cd ~/Projekte/OpenNextion_Hermes_Dashboard
git status --short
git pull --ff-only
python3 -m unittest discover -s tests -v
bash scripts/pi/firmware-build-connected.sh
```

Es werden **64 Python-Tests** erwartet (56 aus v0.7.1 plus 8 neue Diagnose-Regressionstests). Der Firmware-Build verwendet wie bisher den **inkrementellen Arduino-Buildcache ohne `--clean`**. Ein erfolgreicher Build muss `CONNECTED COMPILE OK` und `NOTHING FLASHED` melden. Anschließend kann optional auch die Offline-Firmware mit `bash scripts/pi/firmware-build-offline.sh` kompiliert werden; **Achtung:** dieser ältere Offline-Build verwendet ausdrücklich einen Clean-Build und ist nicht für den schnellen Connected-Entwicklungsablauf erforderlich.

**Keine Firmware wird automatisch hochgeladen.** Ein späterer tatsächlicher Test der neuen SYSTEM-Seite auf dem Display erfordert bewusstes, separat bestätigtes Flashen nach geprüftem Build und überprüfter Gerätezuordnung. Vorher nichts am laufenden Hermes/TLS-Dienst ändern.

## Hardware-Abnahme nach ausdrücklich freigegebenem Upload

1. WLAN und HTTPS prüfen: STATUS muss echte Pi-Livewerte und gegebenenfalls `TLS OK` zeigen.
2. SYSTEM-Seite fotografieren: Heap aktuell/minimal, größter zusammenhängender Heapblock, PSRAM, TLS-Stackreserve, Laufzeit, Touch-Aktionen.
3. Nach 15–30 Minuten das gleiche Foto erneut machen; auf spontane Neustarts, unerwartet sinkende Reserven und weiterhin flüssigen Touch achten.
4. Ausfalltest nur auf ausdrücklichen Wunsch erneut durchführen; die v0.7-Netzwerklogik wurde nicht verändert.

## Abgrenzung

Die Tests in `tests/test_v08_diagnostics.py` prüfen Quellcode-Verträge, sie ersetzen weder den ESP32-Arduino-Compiler noch einen Hardware-Dauertest. Die ESP32-Stackreserve kann **nicht** über das vorhandene Pi-HTTPS-Monitoringskript ausgelesen werden: sie erscheint auf der lokalen SYSTEM-Seite.
