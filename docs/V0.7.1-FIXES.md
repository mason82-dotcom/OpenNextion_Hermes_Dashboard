# Hermes Touch v0.7.1 – gezielte Fehlerkorrekturen (1 + 2)

Dieses Update enthält **ausschließlich die zwei genehmigten Korrekturen**:
1. Connected-Firmware-Upload darf keine veraltete Binärdatei akzeptieren, insbesondere nach Änderungen an `TelemetryWorker.h`.
2. Gecachte Hermes-Healthchecks in der lokalen Pi-Bridge dürfen nach Ausfall des Probe-Workers nicht unbegrenzt einen alten gesunden Status anzeigen.

**Bestätigter Stand (Raspberry Pi 5):** Der Anwender hat nach dem Update die gesamte Testsuite **56/56 Tests in 1,448 s – OK** sowie den inkrementellen verbundenen Firmware-Build mit **`CONNECTED COMPILE OK`** erfolgreich ausgeführt. Nach dem Neustart von Bridge und TLS-Dienst bestätigte `bash scripts/pi/tls-smoke.sh` CA-/IP-validiertes HTTPS, Hermes-API und Dashboard erreichbar, Gateway ON, `probe_fresh: True`, `probe_age_s: 14.6` und `dashboard_reason: ok`. `Chat enabled: False`. **Kein erneutes Flashen.** Die 45-Sekunden-Ablaufregel ist durch Regressionstests verifiziert; eine reale Ausfallsimulation des Probe-Workers steht noch aus.

**Nicht umgesetzt:** eine strengere Loopback-Bindungsregel (früherer Vorschlag 3). TLS-Konfiguration, Firmware/Touch-Oberfläche und Chat-Rechte bleiben unverändert.

## 1. Vollständiger Connected-Firmware-Fingerabdruck

Ein separates, lesendes Skript `scripts/pi/firmware-source-fingerprint.py` erstellt einen SHA-256-Fingerabdruck aus den tatsächlichen Bytes aller lokalen `.ino`, `.h`, `.hpp`, `.c`, `.cc`, `.cpp`-Dateien im Sketch-Verzeichnis sowie dem Connected-Build-Skript und dem Fingerabdruck-Helfer. Dazu gehören insbesondere `TelemetryWorker.h`, `BoardConfig.h`, `Config.h`, `LocalCa.h` und `build_opt.h`. Die Berechnung gibt **keine** Quelldateien oder Zugangsdaten aus.

Nach einem **erfolgreichen** Connected-Build legt das Skript im privaten, von Git ignorierten Build-Verzeichnis die Datei `build/firmware-connected/.connected-sources.sha256` an. Vor und nach dem Kompilieren wird derselbe Quellstand geprüft; ändern sich Dateien während des Builds, wird kein gültiger Fingerabdruck hinterlegt. Ein fehlgeschlagener Build entfernt die bisherige Upload-Freigabe.

Das **manuelle** Upload-Skript verweigert den Flash-Vorgang, wenn dieser Fingerabdruck fehlt oder von den aktuellen lokalen Dateien abweicht. Es erkennt auch Inhaltsänderungen bei **unverändertem Dateidatum**. Die bestehende explizite Flash-Bestätigung `FLASH-HERMES-TLS` bleibt erhalten.

**Wichtig:** Das frühere Connected-Build-Artefakt ist nach dem Update absichtlich nicht mehr durch das Upload-Skript freigegeben. Einmaliges erfolgreiches erneutes Kompilieren ist notwendig, auch wenn die Firmware selbst nicht verändert wurde. `--clean` bleibt weiterhin entfernt (inkrementeller Arduino-Cache).

Der Quell-Fingerabdruck ersetzt keine reproduzierbare Toolchain-Sperrdatei für alle externen Libraries. Er verhindert gezielt die Verwendung älterer lokaler Firmware-Eingabedateien.

## 2. Abgelaufene Hermes-Status-Caches

Die Pi-Bridge führt etwa alle 15 s die beiden Gesundheitsprüfungen für Dashboard und Hermes-API durch. Nach vollständig abgeschlossenem Poll speichert sie eine monotone Prüfuhrzeit und den Zeitpunkt als Unix-Sekunden.

Zusätzliche Felder unter `hermes` in der weiterhin kompatiblen JSON-`schema_version: 1`:

- `probe_fresh`: `true`, wenn der vollständige letzte Prüfzyklus nicht älter als 45 Sekunden ist; sonst `false`.
- `probe_age_s`: Sekunden seit dem letzten vollständig abgeschlossenen Prüfzyklus oder `null` vor dem ersten erfolgreichen Zyklus.
- `last_probe_success`: UTC-Unix-Zeitpunkt des letzten vollständig abgeschlossenen Prüfzyklus oder `null`; dies bedeutet **nicht**, dass die Hermes-API in diesem Zyklus gesund war.

Bei fehlendem/abgelaufenem Prüfzyklus markiert die Bridge `api_healthy=false`, `dashboard_status_available=false`, `gateway_running=null` und `dashboard_reason=stale_cache` (beim Start `pending`). Das verhindert eine irreführende Anzeige von weiterhin erreichbarem Hermes/Gateway bei einem abgestürzten Hintergrund-Prüfthread. Pi-Systemwerte werden weiterhin unabhängig direkt aus Linux gelesen.

Eine neue HTTPS-Antwort vom Pi ist nicht automatisch gleichbedeutend mit einem frischen Hermes-Healthcheck. Auch das TLS-Smoketest-Skript druckt deshalb `Hermes probe cache fresh` und `Hermes probe age (s)`.

Bei normalem Betrieb bleibt die v0.7-Anzeige von Hermes, Dashboard und Gateway unverändert.

## Sicher testen und aktivieren (Raspberry Pi 5)

```bash
cd ~/Projekte/OpenNextion_Hermes_Dashboard
git pull --ff-only
python3 -m unittest discover -s tests -v
```

Vorher: 43 Tests. Neu: 13 gezielte Tests (8 für den Fingerabdruck, 5 für den Healthcache), insgesamt **56 Tests**. **Auf dem Raspberry Pi 5 bestätigt:** `Ran 56 tests in 1.448s` und `OK`.

Damit die **laufende** Pi-Bridge die neue Healthcache-Logik benutzt, den Prozess auf `127.0.0.1:8765` in seinem Terminal mit `Strg+C` beenden und dort neu starten:

```bash
bash scripts/pi/run-local.sh
```

Der TLS-Server auf `192.168.178.63:8766` kann normalerweise weiterlaufen: Er ruft die Bridge pro Anfrage auf; ein kurzzeitiges `HTTP 503` während des Bridge-Neustarts ist erwartbar. Anschließend in einem anderen Terminal:

```bash
bash scripts/pi/tls-smoke.sh
```

Es sollten `Hermes probe cache fresh: True` und ein `probe_age_s` von typischerweise unter 20 Sekunden erscheinen, sobald der Hintergrund-Poll abgeschlossen ist. Unmittelbar nach dem Start kann `False`/`None` korrekt sein.

Die Connected-Firmware ist **nicht geändert worden**. Damit aber ein künftiger, bewusst bestätigter Upload wieder freigegeben werden kann, erst nach bestandenen Tests den Fingerabdruck durch einen neuen inkrementellen Build erzeugen:

```bash
bash scripts/pi/firmware-build-connected.sh
```

**Auf dem Raspberry Pi 5 bestätigt:** `CONNECTED COMPILE OK` und `NOTHING FLASHED`. Der erfolgreiche Build erzeugt die private Fingerabdruckdatei im lokalen Build-Verzeichnis. **Nichts wird automatisch geflasht**; bestehende Firmware, Geräte-WLAN, TLS-Zertifikate und Tokens bleiben unverändert.

Wenn Tests oder Build fehlschlagen, die Fehlermeldung ohne `Config.h`, `config/tls.env` und Schlüsseldateien teilen. Kein Flash zur Fehlersuche erforderlich.
