# Hermes Touch v0.7 – Hintergrundabfragen und reaktionsschneller Touch

**Status:** Auf dem Raspberry Pi **35/35 Tests und inkrementeller Connected-Build erfolgreich**; die v0.7-Firmware ist auf dem ONX3248G035 gestartet und liefert echte Pi-Livedaten. Zwei Fotos zeigen `TLS OK`, Hermes-API erreichbar, Dashboard OK, Gateway ON, 52.4 C, 63.8 % RAM, 0.90 Load und ein Datenalter von 3 s sowie `Pi: 53.5 C | 11/24 Werte` im Graphen. **Ausfallverhalten, Wiederherstellung und Langzeit-Stabilität sind noch nicht nachgewiesen.**

## Was sich ändert

- WLAN-Verbindung, NTP, TLS-Handshake, HTTP-GET und JSON-Dekodierung laufen in **einem FreeRTOS-Hintergrundtask** auf dem ESP32-S3 (ca. 14 KB Task-Stack).
- Die LVGL-Hauptschleife bleibt für Touch/Display zuständig und macht **keinerlei WiFi-/HTTP-Aufrufe**.
- Zwischen beiden Tasks wird nur eine kleine `TelemetrySnapshot`-Struktur über einen FreeRTOS-Mutex kopiert. Die Displayseite versucht den Snapshot **ohne Wartezeit** zu lesen.
- Der Hintergrundtask fragt normalerweise alle **5 Sekunden** neue Werte ab. Die Oberfläche aktualisiert ihren Status jede Sekunde. `JETZT AKTUALISIEREN` sendet nur eine Task-Benachrichtigung.
- Ein erfolgreicher Status enthält eine fortlaufende **Sequenznummer**. Die Grafik erhält nur dann einen neuen Punkt, wenn eine **neue** gültige Messung vorliegt – keine mehrfachen Punkte für den gleichen HTTPS-Abruf.
- Nach **15 Sekunden** ohne bestätigte frische Antwort oder nach einem fehlgeschlagenen Abruf werden Pi-Zahlen unterdrückt. Das Display markiert die Verbindung ausdrücklich als nicht aktuell; alte Graphpunkte bleiben nur als Verlauf sichtbar.
- Der Header zeigt **TLS OK** oder einen **WLAN/TLS-Ausfall**; die Statusseite meldet das Alter der letzten guten Messung in Sekunden.
- Das `SYSTEM`-Tab bleibt bei lokalen ESP32-Werten; `CHAT` bleibt gesperrt.

## Sicherheitsgrenzen bleiben unverändert

- `HT_DEMO_MODE=1` ohne private `Config.h`: keinerlei WLAN-/Hermes-Zugriff.
- `HT_DEMO_MODE=0`: ausschließlich HTTPS mit `setCACert(HT_CA_CERT)`, Zertifikat für Pi-IP, Zeitprüfung per NTP.
- Kein `setInsecure()`, kein HTTP-Fallback und **keine HTTP-Redirects**, die einen Geräte-Token weiterleiten könnten.
- Ausschließlich `GET /v1/status`; kein Chat, keine Start/Stop/Schreiboperationen.
- Bestehende `firmware/HermesTouch/Config.h` und `LocalCa.h` werden **nicht geändert**. Du brauchst weder neue WLAN-Zugangsdaten noch neue Zertifikate.

## 1. Code und Tests auf dem Pi

```bash
cd ~/Projekte/OpenNextion_Hermes_Dashboard
git status --short
git pull --ff-only
python3 -m unittest discover -s tests -v
bash scripts/pi/tls-smoke.sh
```

Die Tests prüfen u.a., dass HTTPS ausschließlich im Worker aufgerufen wird, der LVGL-Loop Netzwerkaufrufe nicht ausführt, der Mutex eine nichtblockierende GUI-Snapshot-Leseoperation hat und veraltete Werte sichtbar als ungültig markiert werden.

## 2. Verbundene Firmware mit vorhandener Konfiguration kompilieren

```bash
bash scripts/pi/firmware-build-connected.sh
```

Das Skript verwendet weiterhin die **inkrementelle Arduino-Kompilierung** ohne `--clean`. Nach `CONNECTED COMPILE OK` liegen die privaten Binärdateien unter `build/firmware-connected/`.

**Keine Firmware wird automatisch geflasht.** Compilerfehler zuerst anhand von `build/logs/firmware-connected-build.log` beheben; keinerlei Zugangsdaten/Token oder komplette private Header veröffentlichen.

## 3. Erst nach grünem Build manuell flashen

Vor dem Flashen sicherstellen, dass der USB-Seriell-Adapter wirklich zum zuvor identifizierten OpenNextion gehört.

```bash
ls -l /dev/serial/by-id/
bash scripts/pi/firmware-upload-connected.sh \
  /dev/serial/by-id/usb-1a86_USB_Serial-if00-port0
```

Die interaktive Freigabe lautet weiterhin `FLASH-HERMES-TLS`. Der alte funktionierende Stand v0.6 wird dabei ersetzt; bei Problemen kann er durch Neubau des entsprechenden früheren Git-Commits wiederhergestellt werden.

## 4. Funktions- und Ausfalltest

**Normalbetrieb (bereits auf Gerät dokumentiert):** SSL/TLS-Anzeige, API- und Gateway-Status, CPU-/RAM-/Load-Zahlen und Temperaturkurve funktionieren. Die beobachteten Touch-Aktionen und die Navigation zur Graphseite zeigen erfolgreiche Bedienung unter normalen Bedingungen. Der Test einer absichtlich langsamen bzw. unterbrochenen Verbindung steht aus.

**Empfohlene sichere Reihenfolge für den nächsten Test:** Aktuelle Statusseite fotografieren, TLS-Server in seinem eigenen Terminal mit `Strg+C` stoppen, 10–20 Sekunden beobachten und in dieser Zeit mehrfach die Reiter wechseln. Den Server **unmittelbar danach** wieder mit `bash scripts/pi/run-tls.sh` starten und die automatische Rückkehr zu `TLS OK` prüfen. Die Bridge auf 127.0.0.1:8765 und Hermes selbst nicht stoppen. TLS-Zertifikat, Gerätekonfiguration und WLAN-Passwort nicht verändern.



1. **Normalbetrieb:** `TLS OK`, Hermes-API-Status und numerische Pi-Temperatur, RAM, Load sichtbar; die Fußzeile zeigt `Pi/TLS | vor N s`.
2. **GRAPH:** Nach 30–60 Sekunden mehrere Messpunkte; keine künstliche Erhöhung zwischen echten HTTPS-Antworten. `VERLAUF ZURUECKSETZEN` testweise antippen.
3. **Touch:** Während einer Aktualisierung schnell zwischen STATUS, GRAPH, SYSTEM, CHAT wechseln; Touch darf nicht mehrere Sekunden hängen.
4. **TLS-Testausfall (optional und kontrolliert):** Den separaten TLS-Statusdienst mit `Strg+C` anhalten (**nicht den Hermes-Agent stoppen**). Nach wenigen Sekunden muss das Display `BRIDGE NICHT ERREICHBAR` und `--` statt veralteter Livezahlen zeigen. Die Touch-Bedienung muss weiter funktionieren.
5. **Wiederherstellung:** `bash scripts/pi/run-tls.sh` neu starten. Nach erneut erfolgreichem HTTPS-Status sollen die Livezahlen automatisch zurückkehren.
6. **Längerer Test:** Freien Heap und PSRAM unter SYSTEM für 15–30 Minuten beobachten. Wiederholte Neustarts oder stetig sinkender freier Heap wären ein Fehler.

Auf dem Pi müssen die Dienste `127.0.0.1:8765` und `192.168.178.63:8766` laufen. Eine neue TLS-PKI ist **nicht** erforderlich.

## Bekannte Grenzen / Prüfpunkte

- Der Worker verwendet noch synchrones HTTPS, aber nur **außerhalb** des LVGL-Tasks. Ein Timeout kann eine einzelne Worker-Abfrage verzögern, nicht die Touch-Ereignisverarbeitung.
- Das Diagramm zeichnet weiterhin die CPU-Temperatur auf einer festen 0–100-°C-Skala. Dynamische Skalierung ist später möglich.
- Die Messabstände sind ungefähr fünf Sekunden nach Abschluss eines Abrufs; bei Netzwerklatenz können sie länger sein.
- Bei fehlender/ungültiger Pi-Antwort wird kein alter Zahlenwert als aktuelle Messung ausgegeben.
- Ein erfolgreich kompilierter FreeRTOS-/WiFiClientSecure-Worker garantiert noch keinen Hardware-Dauertest. Erst reale Tests bestätigen Stackgröße, Speicherverhalten und Touch-Reaktionszeit.
